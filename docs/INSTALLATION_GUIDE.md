# PHP版リンク検査スクリプト 導入マニュアル

このスクリプトは、サーバーで夜間にWordPressの公開ページ内のリンクを検査し、通知対象がある場合に結果をメールで送ります。全件検査の間、手元のPCやSSH接続を開いて待つ必要はありません。

導入は次の順に進めます。

1. サーバーの実行環境を確認する。
2. ファイルを公開領域外に配置する。
3. 自分のサイトとメールの設定を作る。
4. 1ページを手動で検査し、結果保存とメール受信を確認する。
5. 夜間にcronで全件初回テストを行う。
6. 結果と受信を確認する。初回成功後は次回から通常通知へ自動で切り替わる。

最初は1サイトだけで確認してください。検査結果を理由に、記事の編集やリンクの削除を自動で行うことはありません。

## 1. 用意するもの

- SSHとcronを利用できるサーバー
- PHP CLI 8.4以上
- PHP拡張：curl、dom、libxml、XMLReader、intl、mbstring、zlib、pcntl、openssl
- PHPから利用できるCA証明書と、実行可能なsendmail互換コマンド
- 検査する自分の公開サイトと、そのサイトマップURL
- 結果を受け取るメールアドレスと、サーバーで利用できる送信元アドレス

必要な関数や拡張が利用可能かどうかは、後述の `--check` で確認します。WordPress用のPHPと、SSH・cronから起動するPHP CLIは異なる場合があります。PHPの絶対パス、メール送信の可否、cronのタイムゾーンは、利用するサーバーの案内で確認してください。

不足がある場合は、サーバーが対応するPHP CLIや起動方法を確認します。検査のために、既存のWeb用PHP設定を一括で変更しないでください。

## 2. サーバーへ配置する

ダウンロードしたファイルを展開し、SFTPなどで公開領域外へ転送します。以下は配置例です。

```text
/home/USER/wordpress_link_check/
  bin/
  conf/
  lib/
  docs/
```

`bin/` と `lib/` は、配布された構成を保って配置してください。`public_html` など、ブラウザからアクセスできる場所には置きません。設定・結果・ログにメールアドレスやURLのクエリ情報が含まれるためです。

実行ユーザーが配置先へ読み書きできることを確認します。新規の結果ファイルは所有者のみ読み書き可能、保存用ディレクトリは所有者のみアクセス可能な権限で作成されます。導入のために777などの広い権限を付ける必要はありません。

以下の例の `/home/USER/wordpress_link_check` と `/PATH/TO/php` は、自分の配置先とPHP CLIの絶対パスへ置き換えてください。PHP起動用の補助スクリプトを利用する環境では、`--php-bin` にその絶対パスを指定します。

## 3. 本番用の設定を作る

SSH端末で配置先へ移動し、設定例をコピーします。以後、`USER`、`/PATH/TO/php`、サイトURL、メールアドレスは利用環境の値へ置き換えてください。

```sh
cd /home/USER/wordpress_link_check
cp conf/linkcheck_php_example.json conf/linkcheck_php_mysite.json
```

コピーした `conf/linkcheck_php_mysite.json` をテキストエディターで編集します。

最低限、次を自分のサイトに合わせて変更します。

| 項目 | 設定内容 |
|---|---|
| `site_id` | 保存先を区別する識別名。例：`mysite`。半角英数字・ハイフン・アンダースコアを使用 |
| `site_url` | 自分のサイトのトップページURL |
| `collection` | 本番の全件テストは `"sitemap"` |
| `sitemap_urls` | 実際に使うサイトマップURLの配列 |
| `mail.to` | 結果を受け取るアドレス1件 |
| `mail.from` | サーバーで送信元として利用できるアドレス1件 |
| `mail.sendmail_path` | sendmail互換コマンドの絶対パス |

設定例の `example.com` と `CHANGE_ME@example.com` を実際の値へ変更してください。JSONではコメントや末尾の余分なカンマを使えません。

そのほか、次の点を確認します。

- `additional_urls`：サイトマップに含まれない公開ページを追加する場合に指定します。
- `exclude_patterns`：サイト固有の操作用URLなど、アクセスさせたくないURLを必要に応じて除外します。
- `output_dir`：既定の `reports/linkcheck_php` は配置先を基準に解決されます。変更する場合も公開領域外を指定します。
- `request_interval` と時間・件数の上限：最初は設定例の値を維持します。実行時間上限の既定値は2時間です。

サイトマップ方式は、指定したサイトマップに収録されたページとトップページなどを対象にします。サイト内の全URLを自動的に網羅する保証はありません。管理画面・ログイン後のページ・JavaScriptで生成されるリンクなどは、検査対象にできない場合があります。

Amazon関連の直接リンク・短縮リンクは、クリック集計への影響を避けるため通信前に除外します。検査結果の除外は、リンク先が正常であることを意味しません。

### 手動用と本番用の設定を分ける

手動用設定は次の手順5で作ります。両方のファイルを開き、次の対応を確認してください。

| 項目 | 手動テスト用 | 本番用 |
|---|---|---|
| 設定ファイル | `conf/linkcheck_php_manual.json` | `conf/linkcheck_php_mysite.json` |
| `site_id` | `mysite-manual` | `mysite` |
| `site_url` | 検査する公開ページ1件 | サイトのトップページ |
| `collection` | `"urls"` | `"sitemap"` |
| `sitemap_urls` | `[]` | 実際のサイトマップURLの配列 |
| `additional_urls` | `[]` | 必要な追加ページ。不要なら `[]` |
| `crawl_internal` | `false` | 初期導入では `false` |
| `check_images` | `false` | 初期導入では `false` |
| `mail` | 実際の宛先・送信元・sendmailパス | 同じメール設定 |

初回通知の受付記録は設定ファイル名ではなく `site_id` ごとに保存されます。自動判定なしの通常起動では、同じ識別名を使うと1ページだけの記録でも起動が許可されてしまいます。保存先だけを変えても受付記録は分かれません。必ず識別名を分けてください。

自動初回判定では `site_id`・宛先・送信元と、既定値を含む適用設定の内容を照合します。別の検査範囲で作った記録や旧版の記録では、自動切替しません。設定ファイルの場所やJSONの空白・キー順だけの変更は再テストの理由にしません。検査完了は設定した範囲に対するものであり、実際の対象は夜間の保存結果でも確認します。

本番用の設定が上表と一致し、例示URL・メールアドレスが残っていなければ、設定チェックへ進みます。

## 4. 設定と実行環境を確認する

サーバーのSSH端末で実行します。

```sh
cd /home/USER/wordpress_link_check

/bin/sh bin/run_linkcheck.sh \
  --php-bin /PATH/TO/php \
  --config conf/linkcheck_php_mysite.json \
  --check
```

「設定・実行環境は有効です」と表示されれば設定チェックは成功です。この確認では、サイトへの検査通信・メール送信・結果ファイルの作成は行いません。設定チェックだけでは、サイトの取得やメールの到着までは確認できません。

エラーが出た場合は、表示されたPHPパス・必要な機能・メール設定などを修正し、チェックをやり直してください。

## 5. 1ページを手動で検査する

[手動テスト手順](MANUAL_TEST_PROCEDURE.md) に従って実施します。要点は次のとおりです。

- 本番とは別の `site_id` と設定ファイルを使います。
- `collection` を `"urls"`、`additional_urls` を空配列、`crawl_internal` を `false` にし、指定した1ページだけを掲載元にします。
- 設定チェック後、`--initial-test` を付けて手動実行します。
- 実行前後に設定ファイル名・`site_id`・1ページ限定を照合し、検査完了・結果保存・メール配送受付・実際の受信を確認します。

手動手順の合格条件をすべて満たしたら、夜間の全件初回テストへ進みます。不一致があれば、動作成功だけで合格とせず、設定を直して手動テストをやり直します。

1ページでも、そのページ内のリンク数や再確認の待機によって数分以上かかる場合があります。リンクの少ない公開ページを選ぶと、導入時の動作確認を小さい範囲で行えます。

この段階でサイトマップによる全件検査を手動実行する必要はありません。ローカルPCで動作確認する場合も1ページ程度に限定し、メール配送は実運用するサーバーで確認します。

## 6. 夜間に全件検査を自動初回判定で起動する

手動テストが合格したら、手順3で作った本番用設定を使います。上表と実ファイルを照合し、`site_id: "mysite"`、`collection: "sitemap"`、実際のサイトマップが指定されていることを確認します。手順4の `--check` を本番用設定で再実行し、成功してからcronへ登録してください。手動テスト用の設定を登録しないでください。

サーバーのcron設定画面またはcrontabで、次のコマンドを夜間に起動するよう登録します。登録前に既存の設定を控え、既存のジョブは残してください。

```sh
/bin/sh /home/USER/wordpress_link_check/bin/run_linkcheck.sh --php-bin /PATH/TO/php --config /home/USER/wordpress_link_check/conf/linkcheck_php_mysite.json --mode cron --auto-initial
```

毎日03:00に起動するcrontabの例です。時刻はサーバーのcronのタイムゾーンに従います。

```cron
0 3 * * * /bin/sh /home/USER/wordpress_link_check/bin/run_linkcheck.sh --php-bin /PATH/TO/php --config /home/USER/wordpress_link_check/conf/linkcheck_php_mysite.json --mode cron --auto-initial
```

`--auto-initial` はcronに残したまま使います。その適用設定での成功記録がない間は初回テストとして実行し、リンク切れがなくても結果メールを送ります。検査が終了コード0または1で完了し、メールの配送受付・最終結果と終了ログの保存・初回記録の保存がすべて成功すると、次回から通常の通知条件になります。cronの書き換えは不要です。

検査未完了・配送失敗・受付不明・保存失敗なら成功記録を作らず、次回も初回として実行します。メールを送れる場合は、検査未完了の理由も本文に記載します。設定・環境不正などで起動できなければ、起動ログや端末表示で確認します。

`--initial-test` は毎回メールを送る強制再テスト用です。自動切替したいcronには指定せず、`--auto-initial` と併用しません。`--check` とも併用しません。

cronで起動するため、PCやSSH接続を開いて待つ必要はありません。`--mode cron` はcron向けの出力方法であり、cronへの登録自体は行いません。

cron設定画面の操作はブログ記事で案内する方針ですが、PHP版の記事の対象・公開URLは未確定です。確認できるまでリンクは掲載しません。登録画面では、利用するサーバーの案内に従って上記の時刻とコマンドを設定してください。

## 7. 翌朝、結果とメールを確認する

まず受信箱を確認します。結果メールでは、対象サイト、検査完了か未完了か、リンク切れなどの件数を確認してください。件名・本文の日本語が読めることも確認します。

結果の要約は次に保存されます。サーバーのファイルマネージャーやSFTPで取得して読むこともできます。

```text
reports/linkcheck_php/<site_id>/<実行日時_一意ID>/summary.md
```

| 確認項目 | 本番初回テストの合格条件 |
|---|---|
| 起動 | 予約した夜間の実行記録がある |
| 設定ファイル | `launcher.*` の `config=` が本番用設定を示す |
| 識別名 | ログ・結果の保存先と要約の適用設定が本番用の `site_id` と一致 |
| 検査範囲 | 要約の適用設定・収集記録が本番用サイトとサイトマップに一致し、sources.tsvで対象の取得状態を確認できる |
| 検査終了 | 要約の検査・最終終了コードが0または1、未完了理由なし |
| 所要時間 | 設定した実行時間上限内に検査が完了している |
| メール配送受付 | 要約の「メール・実行情報」または `status.json` の `mail.state` が `accepted` |
| 実際の受信 | 指定した受信箱に当該実行の結果メールが届いている |

終了コードの意味は次のとおりです。

| コード | 意味 |
|---|---|
| 0 | 設定した範囲の検査完了・問題なし |
| 1 | 設定した範囲の検査完了・要確認あり |
| 2 | 検査または必要な通知が未完了 |
| 3 | 設定・環境の不備、初回未実施、重複起動などで起動できない |

終了コード1でも、検査が完了し配送受付・受信が確認できれば動作テストとしては合格です。判定保留や接続エラーは、リンク切れと確定せず結果を確認してください。外部リンク先のrobots.txtが取得できない場合、本文の検査を保留することがあります。

コード2・3の場合は、導入確認が済んだ状態とは扱いません。原因を解消するまで繰り返し失敗する場合は、対象のcronを一時的に無効にします。特に時間上限で打ち切られている場合は、対象範囲や上限を見直してから再テストします。要求間隔を下げて無理に時間内へ収めないでください。

各行を同じ実行IDの記録で照合します。実際の受信はスクリプトが判定できないため、配送受付まで成功すると受信確認を待たずに次回から通常通知へ移ります。初回テスト合格の判断には、購入者による受信確認も必要です。

検査完了かつ初回通知の配送受付に成功すると、スクリプトが `state/php/<site_id>/initial_notice.json` を作成します。この記録は手動で作成・書き換えないでください。

### メールが届かない場合

未着だけでは、未起動・検査中・検査失敗・配送失敗を区別できません。次の順で確認します。

1. 迷惑メールフォルダーと、設定した宛先を確認する。
2. 今回の `summary.md` または `status.json` で、検査状態とメール受付結果を確認する。
3. 結果がない場合や終了していない場合は、次のログを確認する。

```text
logs/php/<site_id>/launcher.*       起動・終了とcronモードの出力
logs/php/<site_id>/<実行ID>.log     検査・通知の実行記録
logs/php/startup/                  設定確定前などの起動失敗
```

開始記録しかない場合は正常終了と判断しません。結果もログもない場合は、cronの登録内容・実行時刻・絶対パスを確認してください。`accepted` でも未着の場合は、配送受付以降の問題として、送信元の利用条件やサーバー側の配送記録などを確認します。

検査が続いているか分からない状態で、同じ初回テストを繰り返し起動しないでください。問い合わせる場合は、実行日時、終了コード、エラー表示を添え、メールアドレスやURLの機密情報は伏せてください。

## 8. 自動切替後の通常運用を確認する

全件初回テストの成功後も、手順6の `--auto-initial` を付けたcron行をそのまま使います。別の通常用ジョブを追加しないでください。

`status.json` または要約の「メール・実行情報」の `auto_initial` は `true` のまま、`initial_test` が初回時の `true` から、成功後の次の実行で `false` になります。通常時に通知対象がなければ `mail.state` は `not_sent` です。

通常実行では、再確認済みの404/410など通知条件に該当した場合に結果メールを送ります。同じリンク切れが残れば次回も通知します。除外されたAmazonリンクは通知対象になりません。

判定保留・接続エラー・検査未完了だけでは送信しない場合があります。メールが来ないことだけで正常完了とは判断せず、保存された要約やログも定期的に確認してください。

宛先・送信元・検査範囲・時間上限など適用設定の内容を変えると、自動判定は初回に戻ります。次回のcronで変更後の設定を検査して結果メールを送り、成功後は再び通常通知へ移ります。旧版の受付記録しかない場合も、新版で最初の全件テストを行います。

複数サイトはサイトごとに設定と `site_id` を分け、1サイトずつ手動確認と夜間の全件確認を済ませます。起動時刻は実測した所要時間と負荷を踏まえて決め、導入直後から一斉実行しないでください。

## 9. 運用中の確認と停止

- 終了から30日を過ぎたログ・レポートは、同じサイトの次回検査開始時に自動削除します。削除用のcron登録は不要です。長く残したい結果は事前に別の場所へ保存します。実行中・終了不明など削除しない記録は[操作説明](PHP_OPERATIONS.md#保存期間と自動削除)を参照してください。
- `state/` や実行中のロックファイルを、容量整理のために削除しないでください。
- 設定変更後は自動判定で再度初回メールを送るため、変更後の結果と受信を確認します。すぐに再確認したい場合の `--initial-test` は、実通信とメール送信を伴います。
- 今後の定期実行を止める場合は、対象のcronジョブを無効にします。既に動いている検査は、cronの無効化だけでは停止しません。実行中に配置先を削除・上書きしないでください。

詳細な設定・保存ファイル・判定の説明は [PHP版の操作説明](PHP_OPERATIONS.md) を参照してください。
